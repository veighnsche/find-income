# Prototype → current app: UI and UX differences

26 September 2026 · Comparison document, not an implementation task list.

## Scope and evidence

The desired reference is the [connected prototype](../../design/frontend/15-connected-design/README.md), including its [interaction walkthrough](../../design/frontend/15-connected-design/walkthrough.md) and the approved [refined first-use direction](../../design/frontend/05-b-refinement/README.md). **The owner's latest instruction keeps seven steps but changes the last one:** “Review & send” becomes a separate saved-artifacts and manual-handoff page. The app prepares the materials the vacancy actually needs, then tells the owner which website or email destination to use. It must not fill an employer's website, send email, submit a portal form or otherwise contact an employer. The current product is `dashboard/apps/vite-app`. The owner's [prototype screenshot](/Users/vince/Downloads/screencapture-127-0-0-1-4320-2026-09-25-22_59_33.png) and [current-app screenshot](/Users/vince/Downloads/screencapture-127-0-0-1-5173-2026-09-25-22_59_01.png) directly verify the first-use comparison. Later-stage comparisons below come from the prototype and app source, not a live owner walkthrough of those screens.

The target is the **same information hierarchy, controls, navigation, stage progression and return paths through seven steps**: (1) ordinary deterministic forms for what the owner wants and does not want; (2) Muse Spark 1.3 Contributor CLI freely finds real jobs without a fixed board list, and Jev classifies them as recommended, might recommend, might not recommend, not recommended or exceptional unknown; (3) the owner selects interesting jobs; (4) Contributor checks only selected vacancies, how to apply and actual employer questions; (5) Jev suggests saved answers that the owner can edit or add to; (6) Muse Spark 1.3 Standard CLI drafts the route-appropriate custom CV, email or motivation text and/or form values; (7) a separate page saves the produced artifacts and gives verified instructions for the owner to apply manually. Any missing personal fact is asked of the owner; employer questions are not invented. Matching colors, fonts, borders, spacing or fictional content is not required. The prototype's preview banner, checkpoint selector, simulation controls, made-up employers and sending scenarios are study equipment, not product requirements. Its scripted outcomes are not evidence of live job search or document quality.

The current working tree includes uncommitted changes from an earlier interrupted attempt. The source comparison includes them. In particular, the current-tree Jobs removal control and Today saved-research card should not be mistaken for committed baseline behavior. This document changes no application code and does not alter an existing plan.

**Reading the tables:** “Present, different UI” means the underlying step or control exists but is arranged or presented differently. “Missing UI” means the specified user-facing presentation is not in the inspected frontend. “Unverified” means source or the supplied screenshots do not establish the live experience; it is not a claim that a capability is absent.

## What the current app already has

The current frontend is **not** missing the whole recruitment workflow. It has My search, Today, Jobs and Applications routes; a seven-stage component on chosen-role pages; saved search corrections and explicit job finding; grouped job results, selection and a bottom check action; checked-details and editable-answer pages; application preparation, exact editing and rewrite controls. It also has review, explicit send and attempt outcome/history views, which go **beyond the owner's desired stopping point**. These are visible in [the app router](../apps/vite-app/src/App.tsx), [stage mapping](../apps/vite-app/src/pages/role-stages.tsx), [search](../apps/vite-app/src/pages/SearchPage.tsx), [Jobs](../apps/vite-app/src/features/discovery/grouped-jobs.tsx), [Applications](../apps/vite-app/src/pages/ApplicationsPage.tsx), [answers](../apps/vite-app/src/features/answers/AnswersPage.tsx), [preparation](../apps/vite-app/src/features/prepare/PreparePage.tsx), [review](../apps/vite-app/src/features/review/ReviewPage.tsx) and [attempt outcome](../apps/vite-app/src/features/attempts/AttemptOutcome.tsx).

Their existence in code is distinct from prototype UX parity and from a successful live **real-job-to-tailored-materials** journey. The supplied current-app screenshot shows job finding blocked by Muse Contributor readiness. The project's [frontend progress record](vite-frontend-implementation-progress.md) says its connected browser tests used fixtures and did not prove live collection, classification or drafting.

## Exceptions, responsive behavior and evidence limits

The prototype has fictional states for no results, paused search, a role without a detail check, a missing personal date, a portal application, conflicting application addresses, a changed posting and a corrected CV. The current app has various empty, blocked, stale and error components. This source comparison does **not** establish that every relevant exception is presented with the same next action or recovery path. The prototype's disconnected mail, partial send failure and uncertain send scenarios are outside the clarified desired scope because the app must not send. The [walkthrough](../../design/frontend/15-connected-design/walkthrough.md) remains evidence of the prototype's interactions, not an instruction to reintroduce sending or website autofill.

The prototype defines a narrow-screen navigation layout and a fixed selected-jobs bar. The current app has responsive classes and a sticky check section, but no current-app mobile screenshot or owner walkthrough was supplied. Mobile layout, keyboard reachability through long results, and full-document review in the running app remain **unverified**, not declared absent.

The prototype offered alternatives for navigation, reviewing multiple applications, send authorization and hold behavior. The owner has now specified a **separate saved-artifacts page** for manual handoff, with **no automated website entry, send or employer contact**. The send alternatives and post-send holds no longer define desired parity. The exact visual arrangement of several saved jobs remains to be settled in implementation; this document does not select a styling alternative on the owner's behalf.

## What this document establishes

The source and screenshots support a substantial mismatch in the **composition and continuity** of the desired seven-step journey: deterministic goals forms, the first screen, persistent orientation, search-to-results transition, multi-role work area, exact editing, a separate route-dependent artifact handoff and return after a missing fact. The current app also has employer-contact machinery the owner explicitly does not want. These findings do **not** show that the whole workflow is absent, nor do they justify a deletion or missing-work percentage. Code presence and fixture tests do not prove live Contributor job finding, Standard drafting or that an owner can complete the intended journey unaided. Those questions need a separate running-app walkthrough with saved test data; this document does not claim one occurred.
