# Vite frontend implementation plan

25 September 2026. This is the owner-authorized **early implementation plan** for the known job-search-to-send journey. It starts implementation before the later lifecycle and owner task observations are complete. It does not claim the entire recruitment service is designed or that the first connected prototype has been validated with real users.

## Outcome and boundary

Move the active frontend from `apps/web` to the existing React, TypeScript, Tailwind and shadcn base in `apps/vite-app`. Build the agreed seven-stage journey: **Your goals → Find jobs → Select jobs → Check job details → Answer questions → Prepare applications → Review & send**. Today, My search, Jobs and Applications are the first navigable surfaces; the seven labels are progress stages, not seven compulsory page visits. A chosen role retains one identity and its own stage. Only one stage's work occupies the main view at a time, with compact links to other chosen roles.

This first implementation includes the immediate outcome and exact attempted material after a send. The original [page map](../../design/frontend/01-page-overview/README.md) already assigns sent history, replies and later hiring history to Applications; full correspondence, Interviews, Offers and confirmed employment remain later slices. The [connected prototype](../../design/frontend/15-connected-design/README.md) supplies interaction behavior, not production data or code to copy verbatim. Its fictional employers, scripted percentages, hard-coded listing universe and simulated model work must never become live results.

The owner has asked to start now. This overrides the earlier roadmap's sequencing of the **full** frontend plan after every UX study; unresolved alternatives remain recorded as provisional. Do not call the resulting UI proven, or hide a missing backend capability with a fabricated response.

## Verified starting point

- `apps/vite-app` has the shadcn component base and a starter screen, but no recruitment routes, domain state, API client or tests. Its own package manifest and lockfile are not yet wired into the root Bun/Turbo workspace.
- `apps/web` has working session/auth, typed `/api/v1` requests, research activity polling, opportunity decisions, pack viewing and guarded delivery/reconciliation. Reuse these behaviors and contracts; do not carry over its large all-in-one opportunities screen or manual data-entry layout.
- The backend exposes preferences read, Codex research runs/activity/report, opportunity reads and decisions, sourced Jev screening proposals, single-opportunity preparation, application packs, and exact delivery review/approve/send/reconcile. Its public API does **not** yet expose the prototype's four personalized groups and saved reason catalog, distinct checked employer questions, saved-answer matching, direct material edits or coordinated per-role stage state. Several apparent OpenAPI mutations deliberately return unsupported responses; inspect the handler rather than assuming they work.

## Execution model

This is an implementation backlog, not a record of completed work. All boxes start unchecked. Task dependencies below are **AND** conditions: every listed prerequisite must be complete before that task is dispatched. A task includes its focused tests and evidence; a gate checks the connected result. The numbered waves show useful scheduling groups, not global barriers: start a later-wave task as soon as its named dependencies are satisfied.

Keep the original slice order for connected acceptance: **foundation → read-only shell → discovery/selection → checked details and answers → preparation → review/send**. Backend and component work can overlap before those acceptance gates. The immediate milestone remains **G1**; the rest of this list defines subsequent work without expanding the first milestone to the entire journey.

### Implementation lanes and file ownership

Paths below are relative to `dashboard/`. Feature directories are ownership boundaries to establish in A0, not claims that those directories already exist.

| Lane | Responsibility | Exclusive/shared-file ownership |
| --- | --- | --- |
| **A · Foundation, contracts and integration** | Workspace move, auth/API core, server-owned workflow state, contract integration, acceptance gates and final cleanup. | Root manifests/lockfile/Turbo/Vite configuration, Vite manifest/test configuration, central API/session code, `packages/contracts/openapi.yaml`, generated TypeScript/Go, shared store/schema wiring, API registration and `ops/i12/build.sh`. |
| **B · Shared shell and UI primitives** | Navigation, routes, read-only surfaces, stage display, actor/status/activity components and accessibility. | Vite `src/App.tsx`, `src/main.tsx`, global styles, route registration and shared components. Feature lanes supply page exports; B registers them. |
| **C · Discovery and screening** | Research controls/activity, search brief, reason catalog, Jev assessments, four-group Jobs and selection UI. | Discovery/screening feature components and separately assigned backend service/store/HTTP files. |
| **D · Job checks and preparation** | Selected-job checks, actual employer questions, grounded preparation, direct edits and rewrite versions. | Check/preparation feature components and separately assigned backend service/store/HTTP files. |
| **E · Saved answers and matching** | Approved answer library, Jev Choice matching and exact editable answer state. | Answer feature components and separately assigned backend service/store/HTTP files. |
| **F · Review, delivery and attempts** | Complete-material review, explicit sending, reconciliation and attempted-material history. | Review/delivery feature components and separately assigned backend service/store/HTTP files. |

Each lane owns its colocated tests. A assigns named smoke files to feature lanes and owns the shared smoke harness; two agents must not edit the same smoke file concurrently. Backend packages such as `store`, `httpapi` and `codexservice` are shared: assign individual files, not entire packages, before parallel changes. If an existing file must change in two lanes, its named owner integrates both patches serially.

A owns every OpenAPI edit and regeneration of both `packages/contracts/src/generated/api.ts` and `apps/api/internal/httpapi/generated/api.gen.go`. Feature owners supply proposed shapes and handler changes; generated files are never hand-edited. Likewise, route, schema, dependency and global UI changes go through their owner. A contract handoff includes supported operations, errors, versions, provenance, examples and transition rules; proposed contract tasks below still require implementation design, not blind copying of invented DTOs.

**With four coding agents:** begin with A on foundation, B on shared components, C on discovery inventory/work and D on check inventory/work as their prerequisites become ready. After B finishes the shell, that agent can take E while retaining responsibility for small shell integrations. Once contracts are integrated, A's agent can take F between integration duties. C and D continue their feature work. Pause lower-priority lane work for a gate or shared-file integration; six lanes do not require six agents running at once. Keep the next unblocked task in each lane ready for handoff.

## Agent handoff and integration rules

1. Dispatch a task with its ID, lane, completed prerequisites, exact writable files, existing contracts, applicable source-design links, acceptance criteria and test commands. Record its owner and evidence alongside the checkbox. Use the model-selection skill when assigning coding agents.
2. Claim shared files before editing. A integrates contract/schema/registration changes; B integrates shell routes/global components. A feature agent supplies a small proposed patch to the owner when it needs a shared file. Do not have multiple agents regenerate contracts or rewrite the root lockfile concurrently.
3. Contract examples and synthetic employers may be used in isolated tests or development fixtures only. In the live UI, consume supported endpoints and saved records; missing handlers must remain visibly unavailable. A UI task built against a fixture is not connected acceptance.
4. Complete a feature's focused tests with its implementation. Integrate in dependency order, run the applicable gate once, and reopen it only for a relevant change, failure or unresolved concern. Do not run endless review passes.
5. For a difficult design decision, consult Jev SystemOne three fresh times as required by the root `AGENTS.md`: provide all context/evidence; rewrite all explanatory prose while preserving equivalent facts, constraints and alternatives; check the full wording differences; save requests/responses; investigate disagreements. Agreement is advice, not proof. Routine task sequencing does not decide unresolved product alternatives.

## Cross-cutting rules

- Codex chooses job sources, queries, public APIs and career pages. Saving model cost means reusing evidence and assessments, not hard-coding the source universe or results.
- Jev handles supported Choice/Score tasks: listing classification, selecting saved personalized reasons and selecting an approved answer or `none fits`. Codex/LLM handles retrieval, genuine research and grounded drafting. Opening an explanation is a read, not a new model call.
- An LLM working stage shows a clear actor icon, status and the same collapsible activity component. The feed contains observable actions/results/source links and blockers; no hidden reasoning, invented percentages or false live-work claim.
- Navigation and reading never commission work. Search, selected-job checks, preparation, rewrite and send each have clear triggers; contact stays behind full-material review and explicit send.
- Do not require forms for facts Codex can derive or maintain. Preserve optional owner edits to answer boxes and direct application text. Keep unavailable/uncertain states usable without fabricating completion.
- Use one server-owned job/application state contract and typed generated API. Preserve stable opportunity IDs, per-job stage, material version, source provenance and attempt status across reloads and concurrent sessions.

## Verification and release gates

Each slice needs its generated-contract check, focused Go/TypeScript tests for its state transitions, Vite typecheck/lint/build, and a browser task through its useful end state. Check keyboard/focus, long results and the persistent action, refresh/return, empty/blocked/error states and honest status wording. For delivery, verify version and recipient binding, repeat-click behavior, partial outcomes and uncertain reconciliation with a test service before any real employer contact. Use real or representative vacancy evidence to check four-group screening and reason display; do not infer a reliable threshold from the fictional preview. Owner walkthroughs remain necessary to settle navigation/review alternatives and usability claims, but they need not block building the shared foundation and independently useful live slices.

**Immediate implementation target:** complete G0 (slice 0), then G1 (the read-only shell of slice 1). Do not populate production Jobs with the prototype's fictional Harbor/Cedar/Summit cards while the personalized grouping API is absent. The first live search screen may expose the existing research run and activity honestly while the screening contract is built.
