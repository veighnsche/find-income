# Recruitment workflow implementation plan

25 September 2026 · **Planning only. No application implementation is authorized by this document.**

This corrects the execution priorities of the earlier [Vite frontend plan](vite-frontend-implementation-plan.md) against the app now in the repository and the owner's first inspection. The product is a personal recruitment agency: it should learn the owner and the work they want, find real jobs, help pursue chosen roles, and keep the owner's effort to consequential choices. A simulated prototype, green fixture suite, or checked task ledger is useful evidence about code behavior, but is not evidence that the live agency has found and prepared a real opportunity. The [prior progress record](vite-frontend-implementation-progress.md) remains historical evidence; this plan does not erase it or claim this planning task implemented its work.

## The journey to deliver

The everyday path is **Your goals → Find jobs → Select jobs → Check job details → Answer questions → Prepare applications → Review & send**. These are progress stages, not seven mandatory page visits. Each role has a stable identity and one clear current action. A returning owner resumes the useful decision directly; changing a search does not erase previous results, chosen roles, drafts, or attempts. The shared stage indicator marks Codex/LLM work, and the same collapsible activity view shows observable collection, checks and drafting without invented percentages or hidden-reasoning claims.

1. **Know me and my goals.** Codex assembles reusable profile facts from owner-supplied material and keeps them distinct from desired next work. The owner can inspect and correct experience, search requirements and role criteria in context. Codex owns the saved records; the owner is never required to fill a database-style form for facts Codex can handle. A change is visibly saved and survives reload before the next search uses it.
2. **Find and assess real openings.** A primary **Find jobs** action uses the saved brief. Codex chooses sources, queries, public APIs and company career pages freely. For each brief version it authors the personalized rubric and positive, negative and missing-information reason choices once. Jev classifies collected listings and selects supported saved reasons; the explanation opens without another model call. Results go to **Recommended**, **Could be recommended**, **Probably not recommended**, or **Not recommended**. **Unknown** is an exceptional, explained unusable-evidence state, never the default for one missing field. Missing details stay marked for later checking. **Find more jobs** and **Change my search** are ordinary, context-aware actions that retain saved work.
3. **Choose, then check.** The owner can choose any job in any group. Discovery and Jev classification do not check deeper, even for Recommended. Selection alone saves a choice; the explicit **Check chosen jobs** action starts Codex work only for those roles. It reuses evidence, reads the full vacancy and route, identifies relevant gaps, documents, and the employer's **actual** questions. It never invents employer questions. The chosen action remains accessible on long results lists.
4. **Answer, prepare, review.** In Answer questions, Jev selects among owner-approved saved answers plus **no fitting answer** and prefills editable boxes; the owner may change or leave them blank. No Codex/LLM runs in that stage. Prepare may draft unanswered **required** answers only from verified owner facts; optional blank answers may stay blank, and missing facts hold the relevant application. It assembles coherent materials, saves direct exact edits without an LLM, and invokes Codex only on an explicit rewrite request to create a new reviewable version. The owner inspects the exact destination, channel, CV, message, answers and version before explicitly sending. The app records the actual attempt, outcome and exact attempted material; uncertainty is not called delivery and is not retried automatically.

The earlier [operations-first page map](../../design/frontend/01-page-overview/README.md) puts sent history and replies in Applications, with interviews, offers and confirmed employment later in the service. The current seven-stage delivery covers finding work through immediate send outcome. It is **not** the whole recruitment lifecycle. Do not invent the deferred UX or restart the page map while fixing the first journey. The older proposal's automatic investigation when choosing a role is superseded by the explicit selected-job check decision above.

## Execution model and parallel lanes

This checklist is **future implementation work**. Converting the plan into tasks does not authorize application changes, runtime setup, paid calls or test sends. All boxes start unchecked; existing implementation is reused and verified rather than treated as missing. A verify/repair task can finish with evidence that no code change is needed. The previous Vite checklist and progress record remain historical and are not reset.

Task IDs use the `RW-` prefix to distinguish them from the Vite backlog. Every named dependency is required. Waves show scheduling opportunities, not global barriers: after implementation is authorized, dispatch any task whose own dependencies are complete. Keep connected acceptance in journey order. Code and deterministic tests may advance while a live gate is blocked, but that gate stays open.

## Cost, handoff and execution boundaries

Backend, UI and deterministic verification tasks require subsequent implementation authorization; paid exercises additionally require the recorded scope/ceiling and ready runtime. Honor existing authorization rather than asking twice. Any extension beyond that scope or remaining ceiling needs its own authorization. Missing external prerequisites keep only the affected work blocked; they do not justify inventing success or stopping independent safe work.

Use the model-selection skill when dispatching coding agents. For the app's operations, Jev Choice/Score handles supported judgments, deterministic code handles known facts, and Codex handles discovery, source retrieval and grounded drafting. Catalog generation happens once per search-brief version; explanation opens and navigation are reads. Keep cost/usage evidence per real operation, preserve approved owner data boundaries and avoid printing secret values/private source material in shared audit output.

Integrate in dependency order and check off tasks only when their stated evidence exists. A feature agent's “done” message, generated types or a green fixture suite cannot close a live gate. Run a focused check after a relevant change and each required connected gate; repeat only for a new failure, change or unresolved concern. Planning subagents may review this document, but this checklist launches no application implementation workers.

Before a paid canary, execution needs an authorized spend limit, a configured isolated Codex runner, Jev access, source retrieval tools, valid profile evidence and (for materials) model/effort, career root and Typst. A safe test SMTP destination is needed for send verification. Code currently refers to configuration such as `TYPESAFE_API_KEY`, `JOBSEEK_CODEX_MODEL`, `JOBSEEK_CODEX_EFFORT`, `JOBSEEK_APPROVED_CAREER_ROOT` and `JOBSEEK_TYPST_PATH`; these are **requirements to verify**, not proof they are set. Do not read or disclose private values, spend on a live run, or send anything to an employer during planning. UI failures must say “unavailable” or “needs setup” rather than pretend a search succeeded.

## Acceptance and completion language

For each slice, retain generated-contract/type/lint/build checks and focused deterministic state tests. Add a browser task from the owner's starting point through the useful end state, including reload/back navigation, wrong or missing preferences, long lists and persistent Check chosen jobs action, blocked/partial/empty runs, multiple roles at different stages, and no work on passive reads. Record the observed steps and call trace: which actions invoked Codex, Jev or neither; what was saved; which source supports each fact; what the owner had to type; and what remains unavailable. The first slice's gate must catch the exact regression the owner met: **no Change my search, generic search prompt, and no verified real search**. Later gates cover sourced employer questions, editable saved-answer selection without LLM, exact material edits and safe test send.

A completion report separates: **fixture-verified**, **live-integrated**, **owner-walked-through**, and **deferred/blocked**. It includes the actual run evidence and known gaps, not just green test counts or checked boxes. No usability superlative or “working recruitment agency” claim follows from a simulated flow alone. When live integration is blocked, report the configuration or external-state dependency and the narrower behavior that does work. The owner should never discover a missing primary action only after being told the tool is finished.

Settled decisions above do not need another Jev design round. For any genuinely new difficult design decision, however it arises, follow the three fresh, independently worded SystemOne consultations required by [AGENTS.md](../../AGENTS.md), preserve their requests and responses, and investigate disagreement. An owner walkthrough is one possible source of such a decision, not a prerequisite. Avoid repeated consultations on settled questions or diminishing-return reviews, and do not mistake classifier agreement for behavioral proof. No arbitrary score/display threshold, automatic deep-research policy, mandatory three-job cap, or owner-approved page split is inferred here.
